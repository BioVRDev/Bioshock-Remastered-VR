milestone tests `docs/ARCHITECTURE.md` **finding 2** — that `Core.Object` exposes

> **This is the one arc where the failure mode is a CRASH, not a wrong number.**

> validate before trusting, ship default-off. **Run one session per headset

## M3-S1 · Locate `Object::GetPropertyTextByName`

**Status: ✅ DONE — PASSED, 2026-08-10, in one cycle.** ·
**Type:** diagnostic, no visible change

> **Result.** `GetPropertyTextByName` @ **rva `0x7346E0`** on Steam, prologue
> `55 8B EC 83 E4 F8 83 EC`, identical across two launches. All four accessors
> located, four distinct addresses within `0x300` bytes of each other. Stride 12,
> 8 of 8 neighbours agree. Full numbers in `docs/modules/enginebridge.md`.
>
> The one real risk — the row's function slots are **zero on disk** — resolved
> yes on the first attempt: they are written at runtime, in `slot1`.

> **Built differently from this spec, deliberately.** Static analysis of both
> shipped executables — read-only, no headset — found a better anchor than the
> card assumed: the exe contains `L"intUObjectexecGetPropertyTextByName"` (UE2's
> `IMPLEMENT_FUNCTION` symbol) exactly once, and exactly one DWORD points at it,
> from a 12-byte row in the engine's native table. So the scan is **three stages,
> not `FindCalcView`'s six**, and it validates against the table's own
> regularity. Every principle the card set is kept: locate by pattern never by
> RVA, staged, fail closed, log the near misses, one-shot.
>
> Two things the card did not anticipate, both recorded in
> `docs/modules/enginebridge.md`: all four accessors are located (four adjacent
> rows, same code path, free), and **the row's function slots are null on disk**,
> so the tick retries with backoff and dumps the raw rows if they never fill.

### The one idea
Find the function's address and log it. **Call nothing.**

### Why it is separable
Locating and calling have completely different risk profiles. Locating is a
read-only scan whose worst case is a log line saying it found nothing. Calling
can crash the game. Splitting them means a crash in S2 has exactly one new
variable.

### Specification

**1. Locate by pattern, never by RVA.** Reuse the staged FName/string scan in
`Camera/CameraHook.cpp` — anchors `module scan` and `FindCalcView`. That is the
approach that found the camera function on Steam, Epic **and** GOG, while every
hardcoded address failed on at least one (`docs/ENGINE-MAP.md` §
*Storefront divergence*). Do not add a fourth hardcoded address to that table.

**2. Log the address, its RVA, and the bytes at the prologue.** The RVA is what
makes the result portable to another storefront; the prologue bytes are what S2
will verify before it dares call anything.

**3. Log the near misses.** If the scan finds several candidates, log all of
them with their scores. A single confident wrong answer is worse than three
ranked ones.

**4. One-shot.** Scan once at startup or on first observe, lock, stop.

### Falsifiable outcome
`>>> NATIVE: GetPropertyTextByName @ 0x… (rva 0x…) prologue …`, one candidate,
same RVA across two launches.
**No:** zero candidates, or a different address each launch.

### If it fails
Do **not** fall back to a hardcoded address — that is the thing the storefront
table exists to warn about. Try `GetPropertyText` (the `string` overload,
`Object.uc:1886`) instead; it may have a more distinctive signature. If both
fail, M3 is over and M5 (the metadata walk) opens.

### Do not
Call the function · hook anything · write to engine memory · hardcode an RVA.

## M3-S2 · Call it on `Health` and prove the value is live

**Status:** not started · **Type:** diagnostic behind a default-off switch ·
**1 cycle** · **Depends on:** S1

> **The pivotal test of this milestone**, and the first session in the whole arc
> that can crash the game. A clean *no* is still a successful session.

> ## ⚠ READ FIRST — S1 FOUND THE SIGNATURE IS NOT WHAT THIS CARD ASSUMES
>
> The located symbol is `exec`GetPropertyTextByName. In UE2 that is
>
> ```cpp
> void UObject::execGetPropertyTextByName(FFrame& Stack, RESULT_DECL);
> ```
>
> a `__thiscall` member taking a **bytecode frame**, not a string. There is no
> `obj->GetPropertyTextByName('Health')` entry point anywhere to call. The `name`
> parameter has to be supplied through a constructed `FFrame` whose `Code`
> stream yields it, and the result comes back through `RESULT_DECL` rather than
> as a return value.
>
> This does not change the *question* below — `Health`, damage, does the number
> move — and it does not change the risk posture. It changes the mechanism, and
> it means "tune the calling convention" in *If it fails* means **build the frame
> differently**, not try `__stdcall` instead of `__thiscall`. Budget for that
> before deciding this session is one cycle.

### The one idea
Call `GetPropertyTextByName('Health')` on the live pawn, take damage, and see
whether the number moves.

### Why `Health` specifically
It is the discriminator between **"the bridge is broken"** and **"the property
is empty"**, and skipping it is how this costs three cycles instead of one. The
tester can change it on purpose and see the result with their own eyes. Console
`get` already proved it returns `200.0` forever from the class default
(`docs/INVARIANTS.md`), so a value that *tracks damage* is unambiguous proof the
call reached a live instance.

### Specification

**1. Behind an INI switch, default off.** New behaviour ships default-off; this
one can crash, so it is not a preference, it is a requirement.

**2. Verify before calling.** Prologue bytes match what S1 logged, the object is
non-null and its vtable is inside the module. **Fail closed** — on any mismatch,
log once and never call.

> **What S1 actually logged**, so this does not have to be hunted for. Steam,
> two launches, identical:
>
> | Native | RVA | First 8 bytes |
> |---|---|---|
> | `execGetPropertyTextByName` | `0x7346E0` | `55 8B EC 83 E4 F8 83 EC` |
> | `execGetPropertyText` | `0x734640` | `55 8B EC 6A FF 68 18 87` |
> | `execSetPropertyText` | `0x734840` | `55 8B EC 6A FF 68 A0 87` |
> | `execSetPropertyTextByName` | `0x734940` | `55 8B EC 6A FF 68 B8 87` |
>
> Do **not** hardcode these. `EngineBridge_GetPropertyTextByName()` returns the
> live pointer; these are for the prologue comparison and for noticing if a
> future build moves them.

**3. Call on the game thread only**, from `GameState_Observe`, where the existing
probes live. Never from the render thread.

**4. Throttle hard.** Once a second at most. This is a native call into the
engine, not a memory read.

**5. Log the raw returned string**, not a parsed float. If the calling
convention is wrong the raw bytes are the diagnostic.

### What to tell the tester
Enable the switch. Load a save, note the health number on the HUD, take a little
damage — a splicer hit or a fall — then heal. Mark nothing; the log timestamps
it. **Warn them plainly that this build can crash**, and that a crash is a
result rather than a mistake on their part.

### Falsifiable outcome
**Yes:** the logged value matches the HUD and **changes when health changes**.
**No:** it returns empty, returns the class default `200.0` forever, or crashes.
**A crash is a clean no** — record the calling convention that produced it.

### If it fails
Do not tune the calling convention more than twice. Two failed conventions means
the signature assumption is wrong, and M5 opens.

> **Read this before spending that budget.** Given the ⚠ box above, "tune the
> calling convention" means **build the `FFrame` differently** — not try
> `__stdcall` instead of `__thiscall`. The convention is known
> (`__thiscall`, two arguments); the unknown is the frame's shape and how the
> parameter is fed through `Stack.Code`.

### Worth knowing before you design this
`AActor::Move`, `MoveSmooth`, `SetLocation`, `SetRotation`, `SetCollision`,
`SetPhysics` and `PlaySound` are **all present in the exe** as the same kind of
`exec` native, confirmed by S1's scan. **Roomscale is downstream of this
session** — it needs `Move`, a swept collision-checked delta
(`docs/proposals/vr-features-research.md`). So build the frame machinery so a
second caller with a **vector** parameter is easy, rather than hard-wiring it to
a single `name` argument. That is the difference between this milestone
unblocking one detector and unblocking a feature the user actually asked for.

### Do not
Ship it on by default · call it per frame · call `SetPropertyText*` (writing is
not in this milestone) · gate any behaviour on the result yet.

## M3-S3 · Read the controller's `LastPlayerInputContext`

**Status:** not started · **Type:** diagnostic, no visible change · **1 cycle** ·
**Depends on:** S2 returning yes. **Skip entirely if S2 returned no.**

### The one idea
Call the proven bridge on `ShockPlayerController.LastPlayerInputContext` and feed
the result into `kContexts`, which has existed for many sessions and has **never
once received an input**.

### Why this is the payoff
Every scan for this string has been on the **pawn** (`docs/ARCHITECTURE.md`
finding 3, grave 7). The controller copy is declared at
`ShockPlayerController.uc:42` as a plain `string` rather than `travel`,
consistent with being the live working copy — and it has never been examined.

It is also the only lead that covers the **Little Sister rescue**, which pushes
`NullInput` and never enters cinematic mode at all. `NullInput` is already mapped
to `CTX_SCRIPTED` in `kContexts`. The model is built; it needs a value.

### Specification
Read on the observe tick, throttled. Log on transition only, in the existing
`>>> CONTEXT: "name" class=N` format. **Publish it** — the S76 lesson is that
this detector previously read the value, logged it and threw it away, leaving
`g_class` at `CTX_UNKNOWN` forever.

### What to tell the tester
A rescue, a vending machine, a crate, the pause menu, and a normal combat
stretch. Each should produce a *different* context name.

### Falsifiable outcome
**Yes:** distinct, correct context names for those five situations, and
`NullInput` during the rescue.
**No:** empty every time, or one name that never changes.

### If it fails
The pawn scan and the controller read have now both failed, so the field is inert
on this build regardless of where it is read from. Record that and open M5.

### Do not
Gate behaviour (that is M2-S1, which unblocks the moment this returns yes) ·
re-classify `ContainerUIActive` as a menu — it is deliberately `CTX_GAMEPLAY`,
because classifying it as a menu closed the HUD redirect merely on *approaching*
a lootable crate.
