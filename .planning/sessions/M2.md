# M2 — StateBus, and light up the four waiting features

Four sessions. S1 first and **alone** — prove the predicate before anything depends
on it. Each of the other three is separately visible in a headset, so each is its
own cycle. Read only your own section.

Shared context: `CLAUDE.md` (auto-loads, carries the graveyard) ·
`docs/ARCHITECTURE.md` § *StateBus* · `docs/modules/gamestate.md` · the M1 result.

---

## M2-S1 · StateBus — one owner for game state

**Status:** not started · **Type:** refactor, **no behaviour change** · **1 cycle** ·
**Depends on:** M1-S3

Extra context: `docs/INVARIANTS.md` § *Threading and frames* and § *Architecture* ·
`docs/STYLE.md`.

### The one idea
Give game state a single writer and one predicate per question, so the four waiting
features have exactly one input — and prove the predicate before anything depends
on it.

### Why this is needed first
`g_cutscene` is currently written from three unrelated places — the demoted
ViewTarget path, non-latching pitch telemetry, and the reset paths — and consumers
each decide for themselves what "in a cutscene" means. A real signal cannot just be
dropped into that. `GameState_Theater()` also falls back to a name whitelist
requiring a context lock that has never happened.

### Specification

**1. One writer** — `GameState_Observe`, game thread, calling
`EngineBridge_Cinematic()`. Remove the other writers to `g_cutscene`. **Retire them
explicitly in `.planning/DECISIONS.md`** rather than deleting them silently; that
is how dead ideas come back.

**2. Tri-state, one predicate per question.** Carry `true/false/unknown` through —
do not flatten to bool at the boundary. Keep the questions separate: a HUD gate and
a comfort setting do not want the same answer. The
`ContainerUIActive`-classified-as-menu bug is what happens when they share one — it
closed the HUD redirect merely on *approaching* a crate.

**3. Publish, don't share.** Cross-thread reads go through the existing seqlock
pattern, never a loose flag. If every consumer is on the game thread, **say so in
the module doc** so the next session doesn't add a render-thread reader by accident.

**4. Name the source.** Every predicate should be able to say *why* it is true —
`cine`, `context`, `pauser`. A throttled transition dump is what will explain
S2–S4 when a gated feature misbehaves.

**5. Wire `GameState_Cutscene()` and change nothing else.** No consumer changes this
session. Anything already reading it that starts behaving differently is
information: log it, report it, do not "fix" it here.

### Falsifiable outcome
Full route: `>>> STATE:` transitions bracket the bathysphere and injection · **zero
transitions** in combat and at a crate · HUD, camera, aim and input **exactly as
before** (this is a refactor; any visible difference is a bug in it) · config echo
unchanged from M1-S3.

### If it fails
If wiring the real signal changes behaviour by itself, an existing consumer was
depending on `GameState_Cutscene()` being permanently false. **That is a finding** —
record which consumer in `docs/modules/gamestate.md` and `DECISIONS.md`, and handle
it in whichever session owns that consumer.

### Do not
Change what the user sees (that starts at S2) · gate camera or input on draw
signatures (structurally forbidden) · resurrect the ViewTarget or pitch paths as a
"second opinion" (graves 1–3) · delete retired writers without a `DECISIONS.md`
entry carrying the evidence.

## M2-S2 · Gate the HUD on the real signal

**Status:** not started · **Type:** visible · **1 cycle** · **Depends on:** S1

Extra context: **`docs/modules/hud.md` — mandatory before changing anything in the
capture path** · `docs/INVARIANTS.md` § *The HUD square (solved)*.

### The one idea
The HUD gate already exists and has never had a working input. Give it the StateBus
signal and nothing else.

### The trap — three terms already died in this exact gate

| Term | Why it died |
|---|---|
| scene-sampling "world leak guard" | fired **zero** times across 11,682 log lines |
| `DrawHook_NoWorldRender()` | fired once, at startup loading, never during the square |
| `g_gameplayConfirmed` | computed in the fingerprint function, but the gate reads it in `DrawHook_EndFrame` **after** `g_indexedThisFrame` was reset — permanently false, so the HUD never captured at all |

The last is the instructive one: **when borrowing a per-frame counter, check which
function resets it.** If you add anything here, verify ordering before behaviour.

### Also, from the script
`BeginExorcisingGatherer` calls `Level.GetFlashGUIController().HideMovie('HUD')` —
during a rescue the game hides the real HUD itself, so draws reaching the capture in
that window are **not interface at all**. Expect the rescue to need no gating, and
be suspicious if gating appears to help there.

### Specification
- Gate the HUD capture/presentation on the predicate meaning *"the game is
  presenting a cutscene"* — not a general "something is happening" answer.
- **Treat `unknown` as "do not gate".** Current behaviour is correct in ordinary
  play and is the regression baseline.
- INI switch, **default-off**, so the tester can A/B in one session without a
  rebuild. Default on only once seen working.
- One throttled line saying the gate opened or closed, and which predicate did it.

### Falsifiable outcome
HUD hidden during bathysphere and injection, restored after · HUD **completely
normal** in combat, crate, vending machine, pause and rescue · **no duplicate-world
square in any scene** (the regression that matters most) · `CAPTURED: 5d tex=no`
steady in ordinary play · `hud: host found` nonzero · `EYEQ: depth min=1 max=1`.

### If it fails
Wrong only in cutscenes → the predicate is right, the placement is wrong; a
`hud.md` problem, one more session. Wrong in **ordinary play** → revert to
default-off immediately and treat it as a StateBus problem, not a HUD problem.

### Do not
Touch the redirect condition containing `PSSrv0Res(ctx) == nullptr` — that is the
square fix · set `MenuMaxIndexed = 0` (falsified) · set `hq.layerFlags = 0` (an
alpha diagnostic only) · chase the known ammo-counter transparency regression here
(separate backlog item; folding it in breaks one-change-per-cycle).

## M2-S3 · Cutscene anchor, properly gated

**Status:** not started · **Type:** visible · **1 cycle** · **Depends on:** S1

Extra context: `docs/modules/camera.md` · `docs/modules/render.md` ·
`docs/INVARIANTS.md` § *Other* (the `CutsceneTheater=1` entry) and § *Rendering and
geometry*.

### The one idea
`CutsceneTheater` already works — it was falsified only as a **permanent** setting.
Gate it on the real signal so it applies to scripted cutscenes and nothing else.

### What was actually falsified
`CutsceneTheater=1` as a *general* setting forces **every** cutscene onto the flat
quad. That anchors the opening correctly but is wrong for in-world moments, where
the player should stay in the scene. The mechanism is fine; applying it
unconditionally is not. **This session is the gated version** — what the setting was
waiting for.

### Specification
- Gate theater/anchor mode on the StateBus cinematic predicate.
- **Distinguish the two cases if the signal allows it.** Fully-directed cutscenes
  (bathysphere, injection) want anchored flat presentation; in-world scripted
  moments want to stay in the scene. If StateBus cannot yet tell them apart, **ship
  the conservative behaviour** — anchor only where known correct — and record what a
  finer distinction would need. **Do not invent a heuristic to split them**; that is
  how the graveyard grew.
- `unknown` → do not anchor. In-scene is the safe default.
- INI switch, **default-off**, reusing the existing `CutsceneTheater` key if its
  semantics still fit. Log which mode is active.
- Reset carried state when a new world identity appears, as `DeltaClamp` does.

### Falsifiable outcome
- Bathysphere: anchored, comfortable, and **the projector sequence plays** — this is
  the canary, the exact thing `ModYaw` broke.
- Injection: does not hang. **`HeadAimMode=2` starves the scripted pitch gate** (the
  scene waits for the view to pitch down at the syringe and hangs forever; `=1`
  clears it). Confirm and log which mode the test ran with.
- In-world scripted moments: player stays in the scene, no unexpected flattening.
- Ordinary play identical, switch off and on. No eye misalignment,
  `EYEQ: depth min=1 max=1`.

### If it fails
Right for the opening but wrong elsewhere means the signal is too coarse — expected,
and M3's job. **Not a reason to add timing here.** Ship opening-only, default-off,
and record the gap.

### Do not
Enable `CutsceneTheater` unconditionally (the falsified version) · set
`g_fovMode = 1` (submits the real asymmetric frustum against a symmetric render —
severe eye misalignment) · use exclusive fullscreen to fix anything · re-enable
S75/S78/S79 unwind (grave 4) · touch rotation comfort (that is S4).

## M2-S4 · Rotation comfort, gated

**Status:** not started · **Type:** visible · **1 cycle** · **Depends on:** S1

Extra context: **`docs/modules/camera.md`** — mandatory, this touches view, aim and
turning · **`docs/INVARIANTS.md` § *Aim and movement*, all four entries** ·
`docs/ENGINE-MAP.md` § the `Controller.Rotation` warning box.

### The one idea
`ModYaw` and `FreezeGameRotation` are compiled, correct and parked because they
break forced-move sequences. Enable them **only** while a cutscene is running.

### Why they were parked, precisely
`ModYaw=1` zeroes `sThumbRX`, which freezes `Controller.Rotation` (`+0x1E4`).
Forced-move sequences **steer by that field** — so the opening bathysphere walks the
player into the back wall and the projector never plays. `FreezeGameRotation`
requires `ModYaw`, so both are inert by default. The coupling is structural:
`Controller.Rotation` drives view, weapon trace **and** walk direction, and **no
arrangement of that one field separates the three.** Settled — this session does not
try to.

### The genuine tension, stated honestly
The parked settings break *forced-move* sequences, and forced-move sequences may
happen **during** the very cutscenes this gate would open in. So "enable during
cutscenes" is not automatically safe — it may be the worst possible time.
**Resolve by measurement, not design.** The bathysphere is both a cutscene *and* a
forced move, so it is the discriminating test and the first thing to try.

### Specification
- Gate `ModYaw` and `FreezeGameRotation` on the cinematic predicate: active only
  while true, restored the instant it clears.
- **`unknown` → off.** Current default-off behaviour is known-good.
- Restore cleanly on transition, no carried accumulator across the boundary.
  **Advance the aim base before composing view, aim field and hands in the same
  frame** — doing it after leaves the gun a frame of yaw ahead of the view, which
  reads as the weapon swelling and flickering while turning.
- INI switch, **default-off**, separate from the existing `ModYaw` key so the parked
  settings keep their meaning and a tester can compare. Log the transition.

### Falsifiable outcome
**Bathysphere: the player is carried correctly and the projector sequence plays** —
the canary. No forced camera rotation during cutscenes. Ordinary play unchanged with
the switch off *and* on (the gate should never open outside a cutscene). Combat, aim
and locomotion unaffected.

### If it fails
If the bathysphere breaks again, the honest answer is that **cutscene-gating is not
sufficient** — the gate must exclude forced-move sequences, which needs a signal
this arc does not have. Then: leave both settings default-off exactly as now ·
record it in `DECISIONS.md` with the evidence · note in `ROADMAP.md` that comfort
needs a forced-move signal, and that **`ShockPlayerController.bIsForcingPlayerMove`**
(`:47`, beside `ForcePlayerMoveTargetLocation`) is the obvious Tier 0 candidate.

**That is a good outcome** — it converts a vague "comfort is parked" into a named
missing signal with a candidate field.

### Do not
Set `AimSource=2` (cannot exist — heading freezes permanently, bullets fire in one
fixed world direction) · add a body-follow yaw servo (did not feel right, removed) ·
add a pitch servo (runaway loop, froze view and hand) · try to decouple aim from
movement here (needs the M4-S3 measurement; guessing at it cost three sessions).
